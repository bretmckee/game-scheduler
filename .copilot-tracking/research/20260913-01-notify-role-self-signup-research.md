## Key Discoveries

### Self-signup eligibility is a simple per-game property today, not per-user

The task description hypothesized that eligibility might vary per-user (role-gated signups, waitlists, capacity), which would make a single guild-wide notify-role ping inherently unsuppressable per-recipient. **That hard case does not currently exist in this codebase for the join action itself.** The authoritative server-side gate (`services/api/services/games.py` lines 2315-2323, mirrored client-side by `services/bot/views/game_view.py` lines 82/109-111 and re-enforced identically in `services/bot/handlers/join_game.py` lines 193-198) is: **every signup method accepts a self-join for any user unconditionally, except `HOST_SELECTED`, which accepts none.** Capacity/fullness never blocks a join (overflow/waitlist absorbs excess); `ROLE_BASED`'s `signup_priority_role_ids` only affects queue position, not whether the join is accepted. So "can this game's notify-role ping recipients actually do anything?" reduces to a single per-game boolean: `game.signup_method == SignupMethod.HOST_SELECTED`.

The one genuine per-user eligibility mechanism that does exist — `GameSession.allowed_player_role_ids` / `GameTemplate.allowed_player_role_ids`, enforced by `verify_game_access` (`services/api/dependencies/permissions.py` lines 253-272) — only gates the **web app's** API routes and is never checked by the Discord bot's join-button handler at all. It is a real, pre-existing asymmetry worth flagging (see Edge Cases below) but is not the mechanism the reported complaint is about (the complaint is specifically about `HOST_SELECTED` games, where literally nobody can join, not about role-restricted-but-otherwise-open games).

### No existing coupling between `notify_role_ids` and `signup_method`

Both fields live on `GameTemplate` and are copied onto each `GameSession` at creation/clone time, but as two entirely independent values (`services/api/services/games.py` lines 502/556/558 for create, lines 939/959 for clone). A template's `notify_role_ids` is fixed at the template ("game type") level; `signup_method` is chosen per individual game (within the template's `allowed_signup_methods`, itself usually left as "allow all three of `SELF_SIGNUP`/`HOST_SELECTED`/`HOST_SELECTED_WITH_WAITLIST`" per `frontend/src/components/TemplateForm.tsx` lines 232-238). This decoupling is the structural root cause of the reported bug: a host can create a `HOST_SELECTED` game from a template whose `notify_role_ids` was configured with an open-signup game type in mind, and the role still gets pinged.

### Single, shared code choke point for the mention content

`services/bot/formatters/game_message.py::format_game_announcement` (lines 684-807) is the only function that turns `notify_role_ids` into actual mention text (lines 791-797), and it is reached exclusively via `services/bot/events/handlers.py::_create_game_announcement` (lines 1469-1518), which is in turn the single call site used by **both** current Discord-announcement senders (`_handle_game_created` line 145, `AnnouncementLoop._announce` via `services/bot/announcement_loop.py:189`) and **both** message-refresh call sites (`handlers.py` lines 286, 1070) and the archive-channel snapshot (line 1428). A gating change made once, in this one function (or in its caller `_create_game_announcement`), automatically applies everywhere a game announcement's mention content is ever computed — no per-sender duplication risk, and no interaction with the separate, in-flight sender-unification work described in `20260911-01-game-posting-schedule-cleanup-research.md`.

### No configuration surface exists for a toggle — this would be a new field or a pure business rule

`GuildConfiguration` (`shared/models/guild.py` lines 38-60) has no notification-behavior settings whatsoever. There is no per-server admin setting, no per-game-type "suppress ping when host-selected" flag, and no existing boolean anywhere close to this concept. The smallest viable change is therefore a **pure business rule** — no new DB column, no new API field, no new migration — expressed entirely inside `format_game_announcement`/`_create_game_announcement`: compute the mention list from `notify_role_ids` only when `signup_method != SignupMethod.HOST_SELECTED`, and pass `notify_role_ids=[]` (or filter server-side) otherwise. This is a small, additive code change confined to `services/bot/formatters/game_message.py` and/or `services/bot/events/handlers.py`.

## Recommended Approach

Gate the notify-role mention on the game's `signup_method` at the single shared formatting choke point:

- In `services/bot/formatters/game_message.py::format_game_announcement` (or equivalently in its caller, `services/bot/events/handlers.py::_create_game_announcement`), skip building role mentions from `notify_role_ids` when `signup_method == SignupMethod.HOST_SELECTED`. Concretely: change the mention-building loop at lines 791-797 to iterate `notify_role_ids or [] if signup_method != SignupMethod.HOST_SELECTED else []` (or an equivalent short-circuit before the loop), leaving the host/participant mention logic (lines 799-803) untouched.
- The game still posts normally — only the role-mention portion of `content` is omitted; the embed, buttons, and host/participant mentions are unaffected. This directly satisfies the "post the game without the @mention rather than not announcing it at all" framing implied by the complaint (users are annoyed by the un-actionable ping, not by the announcement's existence).
- No new DB column, Alembic migration, Pydantic field, or guild/template config is needed — this is a pure, always-on business rule scoped to the single formatting function, sourced from data (`game.signup_method`, `game.notify_role_ids`) that is already loaded on every code path that reaches it.

## Implementation Guidance

- **Objectives**: Stop pinging a template's `notify_role_ids` for any game whose `signup_method` is `HOST_SELECTED` (the only signup method where no user can self-join), while still posting the announcement normally (embed, buttons, host/participant mentions unchanged).
- **Key Tasks**:
  1. Add the `signup_method != SignupMethod.HOST_SELECTED` gate around the role-mention loop in `services/bot/formatters/game_message.py::format_game_announcement` (lines 791-797) — this is the single choke point reached by every current and future sender/refresh path (see "Single, shared code choke point" above).
  2. Add/adjust unit tests in `tests/unit/services/bot/formatters/test_game_message.py` (which already has `test_format_game_announcement_with_regular_roles`/`_with_mixed_roles`/`_everyone` at lines ~1723-1859, all currently passing `signup_method="SELF_SIGNUP"`) to cover a new `signup_method="HOST_SELECTED"` case asserting no role mention appears in `content` even when `notify_role_ids` is non-empty, plus a regression case confirming `SELF_SIGNUP`/`HOST_SELECTED_WITH_WAITLIST`/`ROLE_BASED` are all unaffected (still ping).
  3. Consider whether `_create_game_announcement` (`services/bot/events/handlers.py` lines 1469-1518) should log/annotate when it suppresses a configured `notify_role_ids` for observability (optional, not required for correctness).
- **Dependencies**: None on the separate, in-flight `20260911-01-game-posting-schedule-cleanup` sender-unification work — that work only changes _which_ code calls `_create_game_announcement`, never _what_ it computes; this change is orthogonal and safe to land independently, before, or after that cleanup.
- **Success Criteria**:
  - Creating (or cloning, or editing into) a `HOST_SELECTED` game with a template `notify_role_ids` configured produces a Discord announcement whose `content` contains the host/participant mentions but never the configured role mention.
  - `SELF_SIGNUP`, `HOST_SELECTED_WITH_WAITLIST`, and `ROLE_BASED` games continue to ping `notify_role_ids` exactly as today (no regression) — these are exactly the methods per `services/api/services/games.py` lines 2317-2320 where a self-join is always accepted.
  - No new DB migration, schema field, or config toggle is introduced.

## Open Questions / Decisions for Implementation Planning

All three items below were raised as open questions during research and have since been **resolved by product decision** (2026-09-13):

1. **Edit-time signup_method transitions — RESOLVED, not a concern.** Editing `HOST_SELECTED` → a joinable `signup_method` after the initial post and having the _next_ refresh newly render the role mention is **correct, intended behavior, not a bug**: the game just became joinable, so the notify role should be pinged at that point. No special-casing (e.g., "only mention once, at first post") is needed. The gate should simply be evaluated fresh on every render of `format_game_announcement`, exactly as planned.
2. **`allowed_player_role_ids` asymmetry — RESOLVED, not a gap.** The Discord bot's join-button handler correctly does not need to independently re-check `allowed_player_role_ids`: Discord is the authority on which roles a user holds and on button interactivity, so if Discord delivers the button-press interaction to the bot at all, the user already holds whatever role Discord's own permission model required to see/press it. This is not an omission and is explicitly out of scope — no change needed here.
3. **Scope of "HOST_SELECTED" framing — RESOLVED, scope confirmed as `HOST_SELECTED` only.** `ROLE_BASED` games give a matching role _signup priority_ (e.g., earlier queue position), but every user can still self-join a `ROLE_BASED` game regardless of role — confirmed consistent with the code comment at `services/api/services/games.py` lines 2315-2320. There is no per-role eligibility restriction to account for, so `ROLE_BASED` correctly continues to ping unconditionally. The fix's scope is confirmed as exactly: suppress the `notify_role_ids` mention only when `signup_method == SignupMethod.HOST_SELECTED`.

## Scope/Complexity Assessment

**Small, additive, code-only change.** No database migration, no new Pydantic/API fields, no new config surface, and no frontend changes are required. The entire fix is a conditional around one existing loop in one function (`services/bot/formatters/game_message.py::format_game_announcement`, lines 791-797), which is already the single shared choke point for every current and planned future Discord-announcement sender and every message-refresh path. Test additions are confined to the existing `tests/unit/services/bot/formatters/test_game_message.py` suite, which already has direct, non-mocked-formatter-logic coverage of the mention-building behavior to extend. Estimated effort: a few hours including tests, not a multi-phase architectural project.
