# Task Research Notes: Game Posting/Scheduling Cleanup (post_at / scheduled_at)

**Task:** Verify and document a design (already converged interactively) that starts from a single MUI DateTimePicker affordance bug and grows into: (1) fixing both date pickers in `GameForm.tsx`, (2) confirming downstream scheduling infra already tolerates past timestamps, (3) unifying the two independent "post to Discord" code paths onto the one that is already race-safe, (4) a hard ordering dependency on migrating `clone_game` first, and (5) a new bucketed metric replacing the now-meaningless `source="immediate"|"deferred"` label. This document verifies every claim against the current codebase; no alternatives are proposed because none were left open by the brainstorming session.

## Key Discoveries

### Project Structure

The relevant surface spans three services sharing one Postgres database: `services/api` (FastAPI, owns `GameSession` creation/editing/cloning and enqueues `bot_action_queue` rows), `services/bot` (discord.py, owns `AnnouncementLoop`, the generic `SchedulerLoop` × 3, and the `bot_action_queue` consumer), and `shared/` (models, `game_schedules.py`, `game_metrics.py` used by both services so the bot image doesn't need to import from `services.api`). `frontend/src/components/GameForm.tsx` is the single shared form component for both create and edit flows; `frontend/src/pages/CloneGame.tsx` is a separate, simpler page with no `post_at` concept.

### BLOCKER — read this before anything else in this document

**`clone_game` (`services/api/services/games.py` lines 877-1014) unconditionally calls `_setup_game_schedules` (line 995) then `_publish_game_created` (line 1012) on every clone, with no `post_at`/`deferred` branch, and `CloneGameRequest` (`services/api/schemas/clone_game.py` lines 38-57) has no `post_at` field at all.** `_publish_game_created` is the _unguarded_ immediate-post path (Part "unguarded path" below). If that path's code — `_publish_game_created`, the `"game_created"` `bot_action_queue` case (`services/bot/bot_action_listener.py` lines 45, 177-178), and `_handle_game_created` (`services/bot/events/handlers.py` lines 121-172) — is deleted before `clone_game` is migrated to the same "always set a concrete `post_at`, let `AnnouncementLoop` pick it up" pattern used everywhere else in this document, **cloning a game will silently stop posting anything to Discord at all**, because there will be no remaining sender for cloned games. This ordering constraint is a hard dependency, not a nice-to-have, and is restated in Implementation Guidance below.

### Two independent Discord-announcement senders exist today, only one is race-safe

- **Guarded ("scheduled") sender** — `AnnouncementLoop._announce` (`services/bot/announcement_loop.py` lines 158-212): `SELECT ... WHERE message_id IS NULL ... FOR UPDATE SKIP LOCKED`, re-checked (`if game is None: return`) immediately before `channel.send(...)`. Cannot double-post against itself or a concurrent invocation of itself.
- **Unguarded ("immediate") sender** — `_handle_game_created` (`services/bot/events/handlers.py` lines 121-172), reached via `_publish_game_created` (`services/api/services/games.py` lines 2425-2438) → `bot_action_queue` row (`action_type="game_created"`) → `services/bot/bot_action_listener.py` dispatch (lines 45, 177-178). Sends to Discord and sets `message_id` with **zero re-check** that `message_id` is still `None` at send time — no lock, no guard, no idempotency check anywhere on this path.
- **The race this enables:** a still-unannounced, deferred game (`message_id IS NULL`, `post_at` in the near future) whose host uses the edit-mode "Post immediately" checkbox (`clear_post_at=True`, `services/api/services/games.py` lines 2157-2173) at the same moment `AnnouncementLoop` independently notices the same game's `post_at` has become due: both paths can decide to send, and because the immediate path has no guard, **both** Discord messages actually get sent. Whichever transaction's `UPDATE ... SET message_id` commits last silently wins the DB column, orphaning the other, already-posted message with no record of it anywhere. Narrow window, but real, not theoretical — verified by reading the actual send code on both sides, not inferred.

### The fix collapses the "immediate vs. deferred" distinction entirely

Once `postAt` (create-mode form field) always carries a concrete value defaulting to "now" (captured once at form mount, same one-time-snapshot idiom the codebase already uses for `scheduledAt` via `getNextHalfHour()`), every newly-created game's `post_at` is, by request time, already `<= now()`. `deferred = post_at is not None and post_at > now()` (`games.py` line 826) is therefore always `False` for such games — the `deferred` branch stops being a meaningfully distinct case; it is simply "`AnnouncementLoop` will find this row due on its very next tick." There is then no remaining reason for a separate, synchronous, unguarded send path to exist. Collapsing onto the single already-guarded `AnnouncementLoop` sender both simplifies the code and closes the Part 5 double-post gap for free — there is only one sender left, and it already takes the row lock and rechecks before sending.

### `post_at IS NULL` is an overloaded, server-side-only sentinel — do not let form changes collide with it

`post_at IS NULL` has two legitimate meanings today, both **server-generated, never client-generated**:

1. A game not yet posted where the host simply left the field empty (the meaning this document's Part 2 change eliminates for the create-game form specifically).
2. A recurrence clone awaiting host confirmation (`clone_game_for_recurrence`, `shared/services/game_schedules.py` line 236, docstring at line 201). Found via `recur_rule IS NOT NULL AND post_at IS NULL` (`services/bot/bot.py` lines 946-951) and surfaced to the frontend as `display_status == "PENDING_CONFIRMATION"` (`services/api/routes/games.py` lines 1291-1300). Confirming sets `post_at = now()` directly (`recurrence_confirmation_view.py` line 84).

Because meaning (2) is generated exclusively server-side at clone-creation time and never by the `CreateGame` form, Part 2's default-value change (`postAt` defaults to `new Date()` instead of `null` in the create form) does not collide with it — the change is correctly scoped to the create-game form only, not to how the schema/service layer interprets `None` elsewhere.

A **separate, related, already-known bug** (out of scope for this cleanup, recorded here only as a follow-up item): `GameForm.tsx`'s edit-mode picker-hide condition (lines 782-808) hides the `postAt` picker only when `initialData?.post_at` is truthy _and_ in the past. Because `post_at` can legitimately be `None` for either meaning (1) (pre-existing immediately-posted games) or (2) (pending-confirmation clones), the picker incorrectly still renders and is editable in both cases — and for case (2) specifically, editing it lets a host set `post_at` directly through the plain edit-save path, which `AnnouncementLoop` will then pick up and post, silently bypassing the intended `recurrence_confirmation_view.py` confirm-button flow.

### Downstream scheduling infra already tolerates past timestamps — nothing there needs to change

- `SchedulerLoop` (`services/bot/scheduler_loop.py`, backing `NotificationSchedule`/`GameStatusSchedule`/`ParticipantActionSchedule` per `services/bot/bot.py` lines 256-284) treats "due 1 second ago" and "due 1 day ago" identically (`_is_due`, lines 136-138: `time_field <= utc_now()`) — the same tolerance it already needs for the bot being offline.
- `_create_game_status_schedules` (`games.py` lines 329-368) creates both status-transition schedules unconditionally, with no past-time check — a game whose `scheduled_at` is already past would still get correct (if immediately-due) IN_PROGRESS/COMPLETED transitions.
- `NotificationScheduleService.populate_schedule` (`services/api/services/notification_schedule.py` lines 51-99) is deliberately more conservative: a reminder window that has already passed (`notification_time <= now`) is silently **skipped at creation**, never created and never fired late.
- `schedule_join_notifications_for_game` (`shared/services/game_schedules.py` lines 111-139) uses a fixed 60-second offset from the join event, independent of `scheduled_at`/`post_at` — entirely unaffected.

## Recommended Approach

This is a converged, already-decided design; there is nothing left to choose between. The approach, in dependency order:

1. **Fix the picker affordance bug for both fields in `GameForm.tsx`** (Part 2): give `postAt` a concrete non-null default (`new Date()`, captured once at mount) and drop `minDateTime={new Date()}` entirely (past values are fine — they mean "post now", already behaviorally identical to today's `None` default); give `scheduledAt` a single frozen "now" snapshot used as both its default value and its `minDateTime`, replacing the live-recomputing `disablePast`. Update `postAt`'s label/helper text since it's no longer optional.
2. **Migrate `clone_game`/`CloneGameRequest` first** (Part 7 — hard prerequisite): give clone creation the same "always has a concrete `post_at`" treatment, defaulting to "now" at clone time, and route its finalize step through "just set `post_at`, let `AnnouncementLoop`'s NOTIFY-driven pickup send it" instead of its current unconditional `_setup_game_schedules` + `_publish_game_created` calls.
3. **Unify `create_game` and the edit-mode "post immediately" action onto the single guarded sender** (Part 6): remove the `deferred` branch from `_persist_and_publish` (status schedules stay unconditional; never call `_setup_game_schedules`/`_publish_game_created` inline — let the row's `post_at` plus the existing NOTIFY trigger drive `AnnouncementLoop`); simplify the edit-mode immediate-post branch to just setting `post_at = now()` and let the same trigger/loop pick it up.
4. **Only after (2) and (3) both land**, delete the now-dead immediate-path code outright: `_publish_game_created`, the `"game_created"` case in `bot_action_listener.py`, and `_handle_game_created` in `services/bot/events/handlers.py`. Do not leave an unguarded sender lying around unused.
5. **Replace the `source="immediate"|"deferred"` label with a new, dedicated `game.posted.scheduled_in` counter** (Part 8), recorded from the sole remaining sender (`AnnouncementLoop._announce`, which already loads both `game.post_at` and `game.created_at`).

## Implementation Guidance

- **Objectives**:
  - Eliminate the disabled-hours picker affordance bug for both `scheduledAt` and `postAt` in `GameForm.tsx`.
  - Make every game (create, edit, clone) always carry a concrete `post_at`, eliminating the `deferred`/"immediate" distinction as a meaningfully separate code path.
  - Unify Discord-announcement posting onto the single already-guarded `AnnouncementLoop` sender, closing the double-post race in Part 5.
  - Replace the metrics `source` label (meaningless once unified) with a dedicated, bucketed "how far in advance was this scheduled" counter.

- **Key Tasks**:
