## Key Discoveries

### Project Structure

`frontend/src/components/GameForm.tsx` is the single shared form component already used both as `CreateGame.tsx` uses it (mode='create', `initialData` from a _template_, multipart submit to `POST /games`) and as `EditGame.tsx` uses it (mode='edit', `initialData` from a _real game_ fetched via `GET /games/:id`, multipart submit to `PUT /games/:id`). `CloneGame.tsx` today is a wholly separate, much smaller component that also fetches from `GET /games/:id` but renders none of `GameForm`'s fields — only new `scheduled_at` plus carryover selects/deadlines — and submits plain JSON to `POST /games/{id}/clone`, which today unconditionally creates and immediately announces.

### GameForm in 'create' mode with a real-game `initialData` mostly "just works," with two concrete gaps

1. **Every edit-only branch is safely inert in create mode** (confirmed by reading every `mode === 'edit'` guard in the file) — no accidental edit-mode behavior leaks in.
2. **The "Schedule Posting (optional)" `DateTimePicker` unconditionally renders in create mode** (`GameForm.tsx` lines 782-808) and there is **no `CloneGameRequest` field to receive its value** — reusing `GameForm` as-is for clone, without either (a) hiding this picker for the clone case or (b) adding a real `post_at` to `CloneGameRequest`/`clone_game` and wiring it through, produces a form control that silently does nothing when the host fills it in. This is the direct point of contact between this feature and the sibling `post_at`-cleanup research (`20260911-01-game-posting-schedule-cleanup-research.md`) — see Reconciliation below.
3. **No image-preview/attached-image indicator exists anywhere in `GameForm`** — confirmed by exhaustive grep; the only related UI (`has_thumbnail`/`has_image`-gated "Remove" buttons) is edit-mode-gated and would not render in create mode even though `initialData.has_thumbnail`/`has_image` would be populated from a real source game. This matches the decided "no replace/remove UI on the clone screen" direction, but it means the host currently gets **zero visual confirmation** an image is being carried over — worth flagging as a UX gap even though it's explicitly out of scope to fix.

### Central open question: participant-list editing conflicts with deadline-carryover's data model

`clone_game`'s `YES_WITH_DEADLINE` carryover (`_apply_deadline_carryover`, lines 1086-1141) depends on **precise identity** of the _source game's real `GameParticipant` rows_: `partition_participants(source_game.participants, source_game.max_players, ...)` computes `players_to_carry`/`waitlist_to_carry` directly from the DB, and `ParticipantActionSchedule`/`NotificationSchedule(notification_type="clone_confirmation")` rows are created per-participant from those exact objects. This entire mechanism is **independent of, and has no path to be informed by, anything a client submits** — there is no participant override field in `CloneGameRequest` today, by design: clone's participant handling and create's participant handling (`initial_participants: list[str]`, resolved fresh via `participant_resolver.resolve_initial_participants`) are two structurally different systems.

If the redesigned clone screen renders `GameForm`'s `EditableParticipantList` pre-populated from the source game's `confirmed_participants`/`waitlist_participants` (via `buildParticipantList`) and lets the host freely add/remove/reorder — as the task description implies ("participants ... shown as already-attached") — a planner must resolve, before implementation, questions this research surfaces but does not answer (out of scope for research):

- What does selecting `player_carryover=NO` do to an already-populated, host-edited participant list — does it clear the editor, or does the server-side `NO` silently discard whatever the host put in the editor for "confirmed" positions (making the editor's confirmed section pure UI theater when `NO` is selected)?
- If a host removes one specific carried-over participant from the editor, does that participant's deadline-carryover schedule (if `YES_WITH_DEADLINE`) still get created, since `_apply_deadline_carryover` works from `source_game.participants`/`partition_participants`, not from the submitted editor list?
- If a host reorders the list, does that reordering have any effect, given the carryover/deadline machinery re-derives confirmed/waitlist order itself from `source_game.max_players`/`signup_method` and ignores client-submitted order entirely today?
- Does the redesigned clone still use `create_game`'s mention-string-resolution path for _newly added_ participants (extending `CloneGameRequest` with something like `initial_participants: list[str]`, resolved the same way `create_game` does) as a **separate, additive** list layered on top of the still-server-derived carryover groups — i.e., two independent participant sources merged at submit time — or does it fully replace the current identity-preserving carryover mechanism with a fresh mention-resolution pass (which would then need its own way to still create per-participant deadline schedules)?

This is the single largest structural ambiguity in the requested design and needs an explicit decision before an implementation plan can be written; it is not resolvable by inspecting the code further, since no code path in the current codebase merges these two participant models today.

### `max_players` override vs. carryover partition — concrete, precise edge case (goal 7)

`clone_game` (`games.py` line 958) calls `partition_participants(source_game.participants, source_game.max_players, signup_method=source_game.signup_method)` — using the **source game's** `max_players`, not any new value. If `CloneGameRequest` grows a `max_players` override (as the task's design direction requires, to match `create_game`'s full field set) and the host increases `max_players` in the same clone submission, the confirmed/waitlist split used for both the "who becomes a real participant now" copy (lines 970-980) and the deadline-carryover groups (`_apply_deadline_carryover`) would **still be computed against the old, smaller `max_players`**, incorrectly leaving newly-fits-under-the-new-cap players classified as overflow/waitlist. Any implementation must change line 958 to use the resolved (override-or-source-default) `max_players` value — this is a precise, one-line-root-cause bug-in-waiting, not a hypothetical.

### `_resolve_game_host` cannot be reused for clone without a signature change

`_resolve_game_host` (`games.py` lines 235-267) is typed `game_data: game_schemas.GameCreateRequest` and reads `game_data.host` directly. Adding a `host` override field to `CloneGameRequest` and wanting bot-manager host-override behavior identical to create's requires either changing this method's parameter type to something both requests satisfy (e.g. a `Protocol`/shared base with a `.host` attribute), or duplicating the ~30-line resolution logic in `clone_game`. Concrete, not hypothetical — confirmed by reading the method signature and its two current uses.

### `clone_game` has zero mention/channel-resolution logic today — a real, not cosmetic, gap for editable free-text fields

`create_game` runs every free-text field (`where`, `description`, `signup_instructions`) through `_resolve_free_text_fields_for_create` (channel-mention + `@mention` + emoji resolution, `games.py` lines 592-675) because those fields arrive as raw, unresolved template/user text. `clone_game` has never needed this because it only ever copies `source_game`'s already-resolved column values verbatim. The moment `title`/`description`/`where`/`signup_instructions` become host-editable overrides on the clone screen, any new `#channel` or `@user` mention the host types must go through the same resolution pipeline (and its `ValidationError`/`invalid_mentions` error-surface contract, which `GameForm` already knows how to render via `validationErrors`/`channelValidationErrors` props) — this is new logic to add to `clone_game`, not something that falls out for free from adding schema fields.

## Reconciliation with `20260911-01-game-posting-schedule-cleanup-research.md`

That document's Part 7 is a **hard, independently-motivated prerequisite**: it already establishes, from direct code reading, that `clone_game` unconditionally calls `_setup_game_schedules` + `_publish_game_created` (the _unguarded_ Discord-announcement sender) with no `post_at`/`deferred` concept, and flags this as a blocker that must be fixed (give `clone_game`/`CloneGameRequest` a real `post_at`, route finalization through the same guarded `AnnouncementLoop` pattern used elsewhere) **before** that document's own plan can delete the unguarded sender.

This research confirms the two efforts **compose, they do not become redundant with each other, and the ordering constraint sharpens rather than disappears**:

1. **They are not redundant.** This feature's redesign only changes _when the host gets to edit fields_ (before vs. after the underlying `clone_game` service call runs) — it does not remove the `clone_game` service call itself, nor its unconditional `_setup_game_schedules`/`_publish_game_created` calls. Whatever game eventually gets created by a submitted, host-reviewed clone form is created via the **same** `clone_game` method, with the **same** immediate-announce behavior, unless the sibling doc's Part 7 fix is also applied. Fixing "when editing happens" and fixing "how/when the created game gets announced" are orthogonal changes to the same method.
2. **The two changes compose, and the ordering gets stricter, not looser, once this redesign lands**, for a reason the sibling doc could not have known: reusing `GameForm` in create-like mode for the clone screen **unconditionally renders a "Schedule Posting (optional)" `DateTimePicker`** (`GameForm.tsx` lines 788-808) that has no effect today because `CloneGameRequest` has no `post_at` field. If this redesign ships _before_ the sibling doc's Part 7 fix, the clone screen would present a functional-looking scheduling control that silently does nothing — a **new, user-visible regression** introduced specifically by adopting `GameForm`'s UI, not merely the sibling doc's already-documented backend race/architecture concern. This means: **the sibling doc's `CloneGameRequest`/`clone_game` `post_at` migration (its Part 7) should be treated as a corequisite of, or a prerequisite to, this redesign's frontend change — not an independent follow-up that can be sequenced arbitrarily later.** Implementing this redesign without it means either (a) hiding/removing the postAt picker specifically for the clone screen (a `GameForm` prop/behavior change not currently supported — there is no prop to suppress that picker in create mode), or (b) accepting the silent-no-op regression, or (c) doing the sibling doc's Part 7 first/alongside.
3. **The reverse composition also holds**: once this redesign's expanded `CloneGameRequest` exists (with `title`/`description`/etc. overrides), the sibling doc's Part 7 migration (adding `post_at` and switching `clone_game`'s finalize step to "just set `post_at`, let `AnnouncementLoop` pick it up") is a small, additive change to the same already-being-modified schema/method — there's no conflict in doing both in the same body of work, and doing them together avoids touching `clone_game`'s finalize logic twice.
4. **`tests/integration/test_clone_game_endpoint.py::test_clone_game_endpoint_publishes_game_created_event`** (lines 188-234) will need to change under the sibling doc's plan regardless of this redesign (it asserts the exact unconditional `bot_action_queue` row the Part 7 fix removes) — this redesign does not add new pressure on that specific test beyond what the sibling doc already identified, but confirms it concretely by inspection.

## Resolved Design Decisions

These were open questions this document flagged as blocking; the user has since decided them. Recorded here so the planning phase does not need to re-ask.

### Participant-list editing: fully editable, host's submitted list is authoritative

Chosen over "read-only carryover + additions only" and "drop deadline-carryover entirely." Concrete semantics that follow from this choice (not independently re-litigated, but the direct, necessary consequences):

- `player_carryover`/`waitlist_carryover` (NO / YES / YES_WITH_DEADLINE) govern only whether the editor is **pre-populated** at screen-load time: `NO` starts the editor without the source game's confirmed/waitlist entries; `YES`/`YES_WITH_DEADLINE` pre-populate it via the existing `buildParticipantList` reconstruction. After that, the editor behaves like `create_game`'s own participant editor — whatever list the host submits (add, remove, reorder any row, carried-over or new) becomes the actual initial roster, positioned by submitted list order (matching `EditableParticipantList`'s existing position-from-order behavior).
- Deadline-carryover scheduling (`ParticipantActionSchedule` + `clone_confirmation` `NotificationSchedule`, when `YES_WITH_DEADLINE` is selected) must be re-derived from the **submitted** list, not `source_game.participants`/`partition_participants` as today: match submitted entries back to source participants by `discord_id`; a deadline schedule is created only for entries that (a) originated from the source game's carryover and (b) are still present in the final submitted list. A submitted entry with no matching source `discord_id` (a host-added new participant) never gets a deadline schedule — that mechanism exists specifically to re-confirm players who already committed to the source game, not to gate brand-new adds.
- Removing a carried-over participant from the editor before submit means exactly that: they are not in the new game and no deadline/reconfirmation schedule is created for them.
- This requires new server-side logic in `clone_game`: today's identity-based `partition_participants`/`_apply_deadline_carryover` pipeline (`games.py` lines 958, 1086-1141) must be replaced or wrapped with a submitted-list-driven variant that still needs `source_game.participants` (to know which submitted `discord_id`s are carryover-eligible) but computes membership/scheduling from the client payload, not purely server-side. This is real new backend work, not a copy-editing change — flag it as such in the plan.

### `post_at`-picker / sibling-doc sequencing: compose together, don't ship this redesign alone first

Per this document's own Reconciliation section, option (c) is the only one without a user-visible regression: the sibling `20260911-01-game-posting-schedule-cleanup-research.md` Part 7 migration (give `clone_game`/`CloneGameRequest` a real `post_at`, route finalization through the guarded `AnnouncementLoop` pattern) ships together with or strictly before this redesign's frontend change. Shipping this redesign's `GameForm`-based clone screen first — with its unconditionally-rendered "Schedule Posting" picker bound to nothing — would introduce a new silent no-op control that doesn't exist today. The planner should treat the sibling doc's Part 7 as in-scope, co-sequenced work for this effort, not a separately-scheduled follow-up.

### Backend architecture revision: reuse `create_game`'s pipeline instead of an override-diff schema

The user reviewed the plan drafted from this document and correctly identified that its backend approach (`CloneGameRequest` as an override-diff from `source_game`, needing an "override-aware field-copy block," a generalized `_resolve_game_host` for two request types, and mention-resolution gated to "only fields the host overrode") was solving a self-inflicted problem. This section supersedes the corresponding parts of "Central open question," "Technical Requirements," and "Implementation Guidance" below — read this section first.

**Why the diff model is unnecessary:** by the time the redesigned `GameForm`-based clone screen is submitted, every field already holds one final, fully-resolved value — the same as a normal `create_game` submission. There is no override-vs-inherit ambiguity left for the backend to reconstruct, because the frontend already did that reconstruction (pre-populating from the source game, then letting the host edit in place). The backend does not need to know or care which fields the host touched.

**Why the roster needs no special carryover logic at all:** confirmed-vs-waitlist is not a stored distinction — it is derived purely at read time by `partition_participants` (`shared/utils/participant_sorting.py` lines 146-186): `confirmed = sorted_all[:max_players]`, `overflow = sorted_all[max_players:]` (or the `HOST_ADDED`-only variant for `HOST_SELECTED_WITH_WAITLIST`). `_create_participant_records` (`games.py` lines 290-320) already just assigns sequential positions to whatever `initial_participants` list `create_game` is given — no waitlist-awareness needed at creation time. Therefore a plain `create_game`-shaped call, given the host's final, possibly-longer-than-`max_players` submitted list (built through `resolve_initial_participants`, the exact same mention-resolution path `create_game` already uses), produces the correct confirmed/waitlist split **for free**. This resolves the "Central open question" section's ambiguities about reordering/removal/adding — the submitted list, in submitted order, drives everything, exactly like a normal create.

**What is genuinely irreducible and must still be added, additively, on top of a `create_game`-shaped call:**

1. **Image carry-over by reference** — if no new file is uploaded on the clone screen and this is a clone, copy `thumbnail_id`/`banner_image_id` from `source_game` + `increment_image_ref`, instead of accepting raw upload bytes. `create_game` has no equivalent concept (it only ever accepts fresh uploads).
2. **Reconfirmation-deadline scheduling** — after the new game's participants are created, match the _final submitted_ discord_ids against `partition_participants(source_game.participants, source_game.max_players, source_game.signup_method).confirmed_real_user_ids` / `.overflow_real_user_ids` (computed against the **source** game, unchanged); for each match, if the corresponding carryover option was `YES_WITH_DEADLINE`, create the `ParticipantActionSchedule`/`clone_confirmation` `NotificationSchedule` pair (`_apply_deadline_carryover`-equivalent, `games.py` lines 1086-1141). A submitted participant with no matching source discord_id (a host-added new player) never gets a deadline schedule. `create_game` has no equivalent concept at all — this is unavoidably new logic.

**Revised shape of `clone_game`:** keep its own distinct permission gate (`can_manage_game` — host/bot-manager/guild-admin may initiate a clone of _this source game_; this is intentionally different from, and stays in addition to, whatever host-permission check happens next) as today. Then construct a fully-resolved request in the same shape `create_game` consumes (reusing `source_game.template_id`, so template-default-fallback for any genuinely-blank field behaves identically to a normal create), and delegate the mechanical work — template loading, host resolution, free-text mention/channel resolution, `resolve_initial_participants`, `_build_game_session`, `_persist_and_publish` — to `create_game`'s real pipeline (either by calling `create_game()` directly with a constructed `GameCreateRequest`, or by both methods sharing the same extracted internal helpers; a planner should decide which is cleaner given `create_game`'s current structure at lines 677-785). Layer the two additive extras (image ref-copy, deadline scheduling) around that call.

**Decided consequence, confirmed with the user:** delegating into `create_game`'s real pipeline means clone will start re-running `create_game`'s own host-role-permission check (`_resolve_game_host` + `check_game_host_permission` against the template's `allowed_host_role_ids`, `games.py` lines 715-736) against the carried-over (or host-overridden) host — a check today's `clone_game` never performs at all (it sets `host_id=source_game.host_id` unconditionally with zero re-validation). **This is an intentional, wanted behavior change**, not an accidental side effect to avoid: today, if a source game's host later loses the role required by the template, every future clone would otherwise silently keep perpetuating an ineligible host forever. The plan should implement this re-check as part of reusing `create_game`'s pipeline, not bypass it.

**What this eliminates from the prior plan draft:** the entire "generalize `_resolve_game_host`'s signature via a Protocol so `CloneGameRequest` and `GameCreateRequest` both satisfy it" phase becomes unnecessary if clone constructs an actual `GameCreateRequest` rather than inventing a parallel schema — there is only one request type to resolve a host from. Likewise, the "override-aware field-copy block" and "mention resolution only for host-overridden fields" phases are no longer needed, since every field is already final by submit time and can go through the exact same `_resolve_free_text_fields_for_create` call `create_game` already makes on the whole payload, with no risk of double-processing already-resolved inherited text (there is no "already-resolved inherited text" anymore — everything is fresh, final user-facing input, same as create).

## Technical Requirements

- `CloneGame.tsx` must be restructured to fetch, in addition to the source game (already done), the guild's channel list (`GET /api/v1/guilds/{guild_id}/channels`) and, if a host-override field is added, the guild's role list (`GET /api/v1/guilds/{guild_id}/roles`) — both patterns already exist verbatim in `EditGame.tsx` lines 150-159.
- `CloneGameRequest` needs new optional override fields for every `GameFormData` field not already present (see diff table), each defaulting to "use source game's value" semantics at the `clone_game` service layer (not at the Pydantic-default layer, since "unset" must mean "inherit from source," not a fixed default like `create_game`'s template-inheritance).
- `clone_game`'s field-copy block (`games.py` lines 925-950) must become override-aware: `title=clone_data.title or source_game.title` (or explicit `is None` checks, matching `create_game`'s own override-resolution style at lines 738-741).
- `partition_participants` call (`games.py` line 958) must use the resolved (override-or-source) `max_players`, not `source_game.max_players` directly, once `max_players` becomes overridable.
- No multipart/`FormData` change needed for the request itself (images aren't re-uploaded); `CloneGameRequest` can remain a plain JSON Pydantic body as it is today.
- The participant-list/carryover composition question (Central open question, above) needs an explicit design decision before implementation; it is not a copy-editing gap.
- The `post_at` picker's unconditional rendering in create mode needs an explicit decision (suppress vs. wire through) tied to the sibling research doc's Part 7.
